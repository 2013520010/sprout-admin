# 新芽 Sprout Admin — 设计文档

> 本文档描述系统的整体架构、模块划分与关键设计决策，帮助使用者与贡献者理解项目。

## 1. 项目定位

一个**生产级权限管理系统脚手架**，目标是让开发者或外包团队能快速拿到一套带 RBAC 权限、JWT 认证、操作日志和代码生成器的后端骨架，直接在其上开发业务。

核心原则：**麻雀虽小，五脏俱全；约定优于配置；能讲清原理。**

## 2. 总体架构

采用经典的分层架构（前后端分离的后端部分）：

```
┌─────────────────────────────────────────┐
│               Controller 层              │  ← 参数校验、@PreAuthorize 鉴权、Swagger 注解
├─────────────────────────────────────────┤
│               Service 层                 │  ← 业务逻辑、事务、RBAC 数据组装
├─────────────────────────────────────────┤
│               Mapper 层                  │  ← MyBatis-Plus BaseMapper + 自定义 SQL
├─────────────────────────────────────────┤
│          MySQL（持久化）/ Redis（缓存）    │
└─────────────────────────────────────────┘
         ↑                    ↑
    JWT 认证过滤器         操作日志 AOP 切面
```

### 关键横切关注点

| 关注点 | 实现方式 |
|--------|----------|
| 认证 | `JwtAuthenticationFilter` 解析令牌 → Redis 加载 `LoginUser` → 写入 `SecurityContext` |
| 鉴权 | Spring Security 6 + `@PreAuthorize("hasAuthority('...')")` |
| 操作日志 | 自定义 `@Log` 注解 + `LogAspect` 环绕切面 |
| 公共字段填充 | MyBatis-Plus `MetaObjectHandler` 自动填充 createTime/updateTime/createBy/updateBy |
| 逻辑删除 | MyBatis-Plus `@TableLogic` |
| 统一返回 | `Result<T>` + 全局异常处理器 `GlobalExceptionHandler` |

## 3. 认证与授权设计（重点）

### 3.1 为什么选 JWT + Redis 的组合？

对比两种常见方案：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 纯 JWT（无状态） | 服务端不存状态，天然可水平扩展 | 无法主动踢人下线、令牌泄漏无法即时失效 |
| 纯 Redis Session | 可主动踢人、集中管理 | 每次请求都查 Redis，有状态 |
| **JWT + Redis（本项目）** | 兼具两者优点 | 需要维护 Redis |

**本项目方案**：JWT 只负责「自包含地传递一个随机 UUID（subject）」，真正的用户信息（角色、权限）存在 Redis，key 为 `login_tokens:{uuid}`。

这样带来两个关键能力：
1. **主动踢人下线**：删除 Redis 中的 key，即使 JWT 没过期，该用户下次请求也会因加载不到 `LoginUser` 而失效。
2. **实时权限生效**：修改用户角色后，删除其 Redis 缓存即可让新权限立即生效，无需重新签发 JWT。

### 3.2 登录流程

```
用户 → POST /auth/login (username, password)
      → 查库校验用户 + BCrypt 校验密码 + 状态校验
      → 加载角色/权限 → 组装 LoginUser
      → 生成 UUID + JWT(subject=UUID) → LoginUser 写入 Redis
      → 返回 token
```

### 3.3 请求鉴权流程

```
请求 → JwtAuthenticationFilter
      → 解析 JWT 得到 UUID → 从 Redis 取 LoginUser
      → 将权限/角色转换为 GrantedAuthority → 写入 SecurityContext
      → @PreAuthorize 校验权限
```

### 3.4 超级管理员的处理

`admin` 角色拥有全部权限：登录时不查 `sys_role_menu` 关联，而是直接查询全部菜单权限标识（`sys_menu.perms`），避免每次新增菜单都要给 admin 重新分配。

## 4. RBAC 权限模型

- **用户 - 角色**：多对多（`sys_user_role`）
- **角色 - 菜单**：多对多（`sys_role_menu`）
- **菜单**分三类：
  - `M` 目录：前端一级路由容器，无权限标识
  - `C` 菜单：前端页面，有路由 + 权限标识（如 `system:user:list`）
  - `F` 按钮：页面内操作，只有权限标识（如 `system:user:add`）

权限标识采用 `模块:实体:动作` 命名规范，如 `system:user:add`、`monitor:operlog:remove`。

## 5. 操作日志设计

通过自定义 `@Log(title, businessType)` 注解标记需要记录的方法，`LogAspect` 环绕切面自动捕获：

- 操作人（从 SecurityContext 取）
- 请求方式、URL、IP
- 请求参数（过滤 MultipartFile、HttpServletRequest 等不可序列化对象）
- 返回结果（超长截断）
- 状态、异常信息、耗时

日志写入 `sys_oper_log`，异步与主业务解耦（当前同步插入，后续可升级为异步 + 消息队列）。

## 6. 代码生成器设计

### 6.1 整体流程

```
连接数据库 → 读取 information_schema 元数据（表、字段、类型、主键）
          → 导入为 gen_table / gen_table_column 配置
          → 用户调整（类名、包名、模块名、作者）
          → Velocity 模板渲染 → 生成 5 个 Java 文件 → 打包 zip 下载
```

### 6.2 关键点

1. **元数据读取**：通过 MySQL `information_schema.tables` / `information_schema.columns` 获取，不依赖具体 ORM。
2. **类型映射**：`bigint→Long`、`datetime→LocalDateTime`、`varchar→String` 等（见 `GenUtils`）。
3. **命名转换**：下划线转驼峰（`user_name` → `userName`）、表名转类名（`sys_goods` → `Goods`）。
4. **基类复用**：生成的实体继承 `BaseEntity`，自动拥有公共字段与逻辑删除，过滤掉 `create_by/create_time/.../deleted` 等列。
5. **模板引擎**：Apache Velocity，模板位于 `resources/templates/vm/`，可自行扩展前端、Mapper XML 等模板。

## 7. 统一响应与异常处理

- `Result<T>`：`{ code, message, data, timestamp }`，code=200 成功。
- 业务异常抛 `BusinessException`，由 `GlobalExceptionHandler` 统一转换为 `Result`。
- 认证失败（401）与权限不足（403）由 `RestAuthenticationEntryPoint` / `RestAccessDeniedHandler` 返回统一 JSON。
